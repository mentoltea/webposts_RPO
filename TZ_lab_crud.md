# Техническое задание на лабораторную работу

**Тема:** Разработка веб-приложения с REST API и клиентской частью (CRUD)

---

## 1. Цель работы

Разработать полноценное веб-приложение, состоящее из серверной части (REST API) и клиентской части (веб-интерфейс), реализующее полный набор CRUD-операций над одной сущностью.

## 2. Предметная область

Предметная область выбирается исполнителем самостоятельно и согласования не требует. Подойдет любая: книги, задачи, фильмы, рецепты, тренировки, клиенты, товары, заметки, животные в приюте и так далее.

Единственное требование: сущность должна иметь не менее четырех полей, включая как минимум одно строковое, одно числовое и одно логическое или дата.

Дальше по тексту в качестве примера используется сущность "Книга". Названия полей и эндпоинтов меняются под выбранную предметку, структура ТЗ остается той же.

## 3. Используемые технологии

Стек выбирается исполнителем свободно. Любой язык, любой фреймворк, любой шаблонизатор или SPA. Ограничений нет, согласование не требуется.

Примеры рабочих связок:

- React (Vite) + Python (FastAPI или Django REST Framework) + PostgreSQL
- React + Laravel (PHP) + MySQL (Чистый Laravel)
- Vue + Node.js (Express) + PostgreSQL
- Чистый JS + ASP.NET Core + SQL Server
- Angular + Spring Boot + MySQL

Обязательное требование к хранению данных: используется именно база данных. Реляционная (PostgreSQL, MySQL, MariaDB, SQLite, SQL Server) или документная (MongoDB) на выбор. Хранение в JSON-файлах, CSV, в памяти процесса или в глобальных переменных не допускается и считается невыполнением работы.

Обмен данными между клиентом и сервером: только HTTP-запросы в формате JSON.

### 3.1 Пример связки React + Python

- клиент: React, собранный через Vite, запросы через fetch или axios, базовый URL API выносится в переменную окружения
- сервер: Python, FastAPI (или Flask, или Django REST Framework)
- работа с БД: SQLAlchemy либо штатная ORM Django, схема таблиц создается миграциями, не руками через клиент СУБД
- база: PostgreSQL, локально или в Docker
- валидация тела запроса через Pydantic-схемы
- клиент и сервер поднимаются на разных портах (например 5173 и 8000), поэтому на сервере включается CORS для адреса клиента

### 3.2 Пример связки Laravel

- сервер: PHP, Laravel, ресурсный контроллер создается командой `php artisan make:controller BookController --api`
- маршруты объявляются в routes/api.php через `Route::apiResource('books', BookController::class)`, это сразу дает все шесть методов
- работа с БД: Eloquent, модель + миграция через `php artisan make:model Book -m`, таблица создается миграцией
- валидация через Form Request или метод validate() в контроллере, ответ с ошибкой 422 или 400
- база: MySQL или PostgreSQL, параметры подключения в .env
- клиент: либо отдельное React/Vue приложение, обращающееся к API, либо Blade-шаблоны с запросами через fetch к своему же API

Оба варианта равнозначны, выбор между ними ни на что в оценке не влияет.

## 4. Модель данных

Сущность **Book** со следующими полями:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| id | integer / uuid | да | Уникальный идентификатор, генерируется сервером |
| title | string | да | Название книги, от 1 до 200 символов |
| author | string | да | Автор, от 1 до 100 символов |
| year | integer | нет | Год издания, от 1450 до текущего года |
| genre | string | нет | Жанр, до 50 символов |
| available | boolean | нет | Признак наличия, по умолчанию true |

## 5. Требования к серверной части

### 5.1 Список эндпоинтов

| Метод | Путь | Назначение |
|---|---|---|
| GET | /api/books | Получить список всех книг |
| GET | /api/books/{id} | Получить одну книгу по идентификатору |
| POST | /api/books | Создать новую книгу |
| PUT | /api/books/{id} | Полностью обновить книгу |
| PATCH | /api/books/{id} | Частично обновить книгу |
| DELETE | /api/books/{id} | Удалить книгу |

### 5.2 Коды ответов

- 200 OK - успешное выполнение GET, PUT, PATCH
- 201 Created - успешное создание ресурса (POST)
- 204 No Content - успешное удаление (DELETE)
- 400 Bad Request - ошибка валидации входных данных
- 404 Not Found - запрашиваемый ресурс не найден
- 500 Internal Server Error - внутренняя ошибка сервера

### 5.3 Формат ответов

Успешный ответ (GET /api/books/1):

```json
{
  "id": 1,
  "title": "Мастер и Маргарита",
  "author": "Михаил Булгаков",
  "year": 1967,
  "genre": "Роман",
  "available": true
}
```

Ответ с ошибкой:

```json
{
  "error": "Validation failed",
  "details": ["Поле title обязательно для заполнения"]
}
```

### 5.4 Дополнительные требования

- Валидация всех входящих данных на стороне сервера. Клиентская валидация не заменяет серверную.
- Настроенный CORS для работы с клиентской частью с другого адреса.
- Сервер не должен падать при некорректном JSON в теле запроса, требуется вернуть 400.
- Идентификаторы не переиспользуются после удаления записи.

## 6. Требования к клиентской части

Интерфейс должен состоять из одной или нескольких страниц и обеспечивать:

1. Отображение списка книг в виде таблицы или карточек. Выводятся все поля кроме id либо вместе с ним.
2. Форму добавления новой книги с полями из раздела 4.
3. Возможность редактирования существующей записи. Форма предзаполняется текущими значениями.
4. Удаление записи с подтверждением действия.
5. Обновление списка после любой операции без перезагрузки страницы вручную.
6. Отображение сообщений об ошибках, полученных от сервера, в понятном пользователю виде.
7. Индикацию загрузки при выполнении запроса.
8. Сообщение о том, что список пуст, если записей нет.

Все запросы к серверу выполняются через fetch или аналогичный механизм асинхронно. Перезагрузка страницы при выполнении операций не допускается.

Оформление интерфейса на усмотрение исполнителя, но интерфейс должен быть читаемым, элементы управления подписаны, формы имеют понятные подписи полей.

## 9. Критерии приемки

Работа считается выполненной, если:

1. Реализованы все шесть эндпоинтов из раздела 5.1 и они корректно отвечают на запросы.
2. Все операции CRUD доступны из веб-интерфейса.
3. Данные сохраняются между перезапусками сервера.
4. Сервер возвращает корректные HTTP-коды в штатных и ошибочных ситуациях.
5. При отправке некорректных данных приложение не завершается аварийно.
6. Код разделен на логические модули, не находится в одном файле целиком.
